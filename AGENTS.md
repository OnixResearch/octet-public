# Agent Notes

## Config and receipt source of truth
- Prefer Nickel over JSON for human-authored config, profiles, fixture matrices, policy knobs, artifact retention, retry/timeout/stage lists, and environment overlays. If humans compose or override it before execution, author it as Nickel and export deterministic tool input from Nickel.
- Prefer Rust-owned DTOs with generated Nickel contracts for emitted receipts, proof/evidence summaries, persisted checkpoints, and other versioned runtime outputs. If Rust emits it after execution and compatibility matters, derive the Nickel contract from Rust instead of hand-authoring JSON schema.
- Raw secrets, cryptographic internals, serialized capabilities, wire discriminants, async/runtime behavior, hot-path constants, and raw logs are non-candidates: keep them out of Nickel-owned config/contracts except as references, handles, paths, allowlists, or explicit exclusion rationale.
- Register every config/receipt family in `standards/policies/registry.ncl` under `config_receipt_families` as `nickel-authored`, `rust-derived`, or `non-candidate`; keep generated artifacts covered by `octet-artifact-manifest.json` freshness checks.

## Build / test
- Run Rust builds inside the nix devshell: `nix develop -c bash -c '...'`. Plain `cargo` outside the shell can miss OpenSSL/pkg-config and rustc-private setup needed by Dylint.
- Pure Nix `checks.nextest` sandboxes here may not provide `/usr/bin/env`; helper scripts and generated wrappers used by tests/templates must resolve an absolute `bash` from `$BASH` or `PATH` instead of hardcoding `#!/usr/bin/env bash`.
- In pure Nix tests here, `$HOME` may be `/homeless-shelter`; cache paths for embedded source extraction must fall back to a writable temp location instead of assuming `~/.cache` is creatable.
- When shared `~/.cargo-target` lock contention or unrelated repo builds interfere, use a temporary `CARGO_TARGET_DIR` with trap-cleanup for reviewable `cargo test --lib` / `cargo test --test ui` runs.
- After adding or removing Cargo dependencies, run `cargo generate-lockfile` before trusting fresh `--locked` Nix builds or `nix flake check`.
- When adding new workspace members or standards fixture trees, stage the new paths before `nix develop` / flake checks; Git-backed flake sources do not include untracked files.
- When adding a workspace member, update standalone source-copy helpers such as `build_standalone_cargo_tigerstyle()` in `tests/consumer_integration.rs`; otherwise Nix `checks.nextest` can copy a root `Cargo.toml` that references a missing member and fail before the tested behavior runs.
- When review needs proof of specific UI cases here, make the saved UI transcript print each fixture name and save a separate artifact that prints snapshot contents; a bare `test ui ... ok` transcript is not enough.
- The custom `tests/ui.rs` harness does not compile `#[cfg(test)]` fixture code unless that fixture gets an explicit `--cfg test`; add per-fixture rustc args when you need to exercise cfg-gated test modules.
- Standalone UI fixtures can use bare lint attrs like `#[allow(no_panic)]`, but tool-scoped forms like `#[allow(tigerstyle::no_panic)]` need `#![feature(register_tool)]` plus `#![register_tool(tigerstyle)]` or rustc rejects them before the lint runs.
- Late-pass block attrs like `#[allow(tigerstyle::no_panic)]` on `{ ... }` attach to the enclosing `hir::Expr` with `ExprKind::Block`, not `hir::Block::hir_id`; candidate collection for block-level escape hatches must inspect the block expression HIR id.
- Test-context suppression must treat only cfg predicates that require `test`; a token match on `test` is too broad and wrongly suppresses cases like `#[cfg(not(test))]`.
- Early-pass line-scan fallback for test context must recognize both outer `#[cfg(test)]` and inner `#![cfg(test)]` attributes when recovering stripped cfgs from source text.
- For same-branch unwrap suppression, a raw condition-snippet search is too broad: `if x.is_some() || other { x.unwrap(); }` is still unsafe. Use condition structure so `&&` can imply the guard, while `||` only counts when both sides require it.
- When a lint needs to recognize `Drop::drop`, compare the enclosing trait impl against `tcx.lang_items().drop_trait()`; matching a trait name string like `Drop` is too loose.
- On this nightly, `AssocItem` does not expose `fn_has_self_parameter`, and `tcx.impl_trait_ref(local_def_id)` is not an `Option`; for method receiver counting or trait-impl skipping in HIR, inspect the parent `ItemKind::Impl(...).of_trait` and `sig.decl.implicit_self` instead.
- For `unchecked_narrowing`, scanning an entire enclosing block for `assert`/`MAX` is too broad and will suppress casts guarded only for other values or later statements; inspect only prior same-block assertions that match the casted expression.
- In late HIR, `assert!(cond)` expands to an `if !cond { ... }`; same-block assert recognition must unwrap that leading `!` instead of looking for a bare binary condition.
- In late HIR, `expr.await` lowers to an `AwaitDesugar` match around `IntoFuture::into_future(<method call>)`; async ignored-result rules should inspect the nested method call rather than looking for a top-level `MethodCall`.
- Tokio `sync::mpsc` public re-exports resolve through internal def paths like `tokio::sync::mpsc::bounded::Sender`, `...::bounded::Receiver`, and `...::unbounded::unbounded_channel`; `get_def_path` matching must use the definition path, not just the public re-export spelling.
- `crossbeam::channel::unbounded()` resolves through the definition path `crossbeam_channel::channel::unbounded`; lint matching must use the source crate def path, not the facade path.
- Late-pass `unbounded_loop` must ignore expansion/desugaring-generated loops or it will falsely warn on compiler-inserted `.await` polling loops.
- User-written `for` loops arrive as `ExprKind::Loop` with `LoopSource::ForLoop`, but their `span.from_expansion()` can still be true because of `ForLoopDesugar`; lints that want real `for` coverage cannot blanket-skip expanded loop spans.
- `tests/ui.rs` can support async/Tokio standalone fixtures by building a sibling fixture-local `Cargo.toml` once, then passing `-L dependency=...` and `--extern tokio=...` while still compiling the actual linted fixture with `--edition=2024`.
- For fixture subdirs like `ui_tests/foo/foo.rs`, the checked-in snapshot path is still `ui_tests/foo.stderr` because the harness keys snapshots by file stem, not full relative path.
- Fixture-local support manifests may depend on sibling path crates, but those nested path crates must NOT declare their own `[workspace]` table or Cargo reports multiple workspace roots under `ui_tests/...`.
- Nix `checks.ui` only vendors dependencies present in the repo root `Cargo.lock`; if a fixture-local support crate depends on `tokio`, add matching root `dev-dependencies` so the vendored sandbox can resolve it.
- The custom `tests/ui.rs` harness now supports snapshot refresh via `BLESS=1 cargo test --test ui -- --ignored --nocapture`; use it inside `nix develop` when updating `.stderr` files.
- `tests/ui.rs` now also has ignored rail `autofix_machine_applicable`; it discovers every checked-in `ui_tests/*.fixed`, runs `cargo fix` in a temporary Cargo crate with the built tigerstyle Dylint wrapper, compares the result to the `.fixed` file, reruns `cargo fix` to prove idempotence, then reruns `cargo check` and asserts zero warnings remain.

## OpenSpec workflow
- Repo-local OpenSpec task guidance now lives at `openspec/templates/tasks.md`; active changes should dogfood that `I<n>` / `V<n>` / `H<n>` shape and end with `## Verification Coverage`.
- `I<n>` tasks are implementation-only units; if a checkbox text says `verify`, `save`, `capture`, `evidence=`, or names an `evidence/` path, split that work into `V<n>` or `H<n>` instead.
- `## Verification Coverage` is scenario-based, not artifact-based: every added or modified scenario heading gets its own row even when multiple rows point at one shared transcript.
- `H<n>` tasks must carry all four replay fields: `command=`, `input=`, `asserts=`, and `evidence=`.
- For OpenSpec gate-fixture proof here, keep the committed fixture under `tests/fixtures/openspec-task-governance/`, temporarily copy it into `openspec/changes/<fixture-name>/` before calling `openspec_gate`, then remove the temporary active change after saving the transcript.
- Shell-launched `pi -p` helpers that rely on `openspec_gate` need explicit `-e ~/.pi/agent/extensions/openspec-gates.ts`; default non-interactive pi startup may omit that tool.
- When cross-family gate reruns are blocked by reviewer quota or current conversation context causes recursive missing-evidence findings, temporarily switch to `reviewer_selection off` and run a fresh `pi --no-session -e ~/.pi/agent/extensions/openspec-gates.ts -p "Call the openspec_gate tool ... Print the full result."`; same-family review avoids the exhausted Claude lane and keeps the transcript free of current-session prompt leakage.
- `openspec archive` can create a new main spec with a placeholder `## Purpose` line (`TBD - created by archiving change ...`); replace that placeholder before committing the archive.
- If a change links contributor docs back to an existing canonical main spec (for example `openspec/specs/performance/spec.md`), say explicitly in the proposal that the main spec already exists and the link targets that canonical file rather than the change-local delta path, or proposal/design gates may treat the spec path as unresolved.
- When a change requires saved deterministic proof artifacts under `evidence/`, make the spec/design name each artifact's exact expected output, not just the file path; gate review treats path-only artifact requirements as underspecified.
- If a spec says a guide or template allows no extra `##` headings, describe the saved headings artifact as the complete extracted second-level-heading inventory after no-extra validation, not just the required heading list; otherwise design review treats the negative condition as unproven.
- If spec acceptance depends on exact link-artifact line order or exact-once human-review labels, restate that order/counting explicitly in design and task output contracts; design review does not assume those details carry over implicitly from the spec.
- Some doc-discoverability V-tasks here grep exact bare Markdown-link lines with `^...$`; when tasks/design use those commands, keep required links on standalone lines rather than bullets or inline sentences or deterministic verification will fail.
- `openspec validate --strict` rejects delta requirements with no `#### Scenario:` blocks, even proof-artifact requirements; give every added/modified requirement at least one scenario and trace it in `## Verification Coverage`.

## Lint registration / config
- Do not implement per-lint severity by registering cloned `Lint` descriptors with patched `default_level`; passes still emit the original static lint IDs, so `allow`/`deny` overrides silently fail.
- In this repo, per-lint severity overrides must keep original lint statics registered and feed effective levels through rustc lint opts before lint-level computation.
- Do not route pass registration through a runtime function-pointer inventory table here; it breaks source-attribute activation for allow-by-default lints in standalone UI fixtures. Keep `LINT_INVENTORY` as the source of truth, but generate explicit registration code from it.
- Tool-scoped group attrs like `#![allow(tigerstyle::safety)]` do not work while the lints are plain `declare_lint!` statics. A naive switch to `declare_tool_lint!` makes those group attrs viable, but it breaks the current per-lint config path that feeds bare names through `sess.opts.lint_opts` and also invalidates existing bare source-attr fixtures.
- Spike proof on 2026-04-15: one lint (`no_unwrap`) can move to `declare_tool_lint!(pub tigerstyle::NO_UNWRAP)` while preserving bare `dylint.toml` keys and bare lint opts by registering a one-member bare alias with `lint_store.register_group(true, "no_unwrap", None, vec![LintId::of(NO_UNWRAP)])`; standalone tool-scoped attrs still need `#![feature(register_tool)]` plus `#![register_tool(tigerstyle)]`.
- Live Aspen consumers still use bare source attrs like `#![allow(no_panic)]` in crate roots (`aspen-time`, `aspen-hlc`, `aspen-core`, `aspen-coordination` at Aspen `bd486f3dc`); any `no_todo` split or escape-hatch migration plan must document bare source-attr migration, not just tool-scoped `tigerstyle::...` attrs.
- Mixed-phase side effect: once any `tigerstyle::...` tool lint is registered, standalone `#![register_tool(tigerstyle)]` attrs for still-plain lints stop taking the old silent MissingTool path and start warning `unknown lint: tigerstyle::<lint>` with suggestions to the bare name; expect snapshot churn like `ui_tests/no_panic_todo_allow.stderr` until those lints migrate too.
- Hard blocker found during bulk conversion on 2026-04-15: `no_panic` cannot keep its current `#[allow(tigerstyle::no_panic)]` + adjacent-comment semantics once it becomes a real tool lint; rustc `allow` suppresses the entire lint before custom justification logic runs. Preserving that contract needs a redesign (for example split `todo!()` into its own lint/marker) or an explicit exception from full tool-lint migration.
- `explicit_defaults` late-pass matching also fires on user-written shorthand that macro-expands to a foreign `Default::default()` call, including Aspen `#[serde(default)]` field attrs; downstream evidence for that lint may point at the source attribute span instead of a spelled-out `Default::default()` call.
- Human-format rustc snapshots do not print `Applicability` by themselves; any reviewable structured-suggestion contract here must add an explicit note like `structured suggestion applicability: MachineApplicable` or reviewers cannot see the tier in `.stderr` artifacts.
- Main OpenSpec spec files here must stay in full spec form (`# ... Specification`, `## Purpose`, `## Requirements`, then direct `### Requirement:` headings). Leaving archive-time main specs in delta form (`## ADDED Requirements` / `## MODIFIED Requirements`) makes `openspec validate --specs` and `openspec archive` fail with `Spec must have at least one requirement`.
